# 本机验证记录

2026-11-07。此记录区分代码验证和真实微信界面验证，不把合成测试当成自动发送验收。

## 已验证

- 原生桥接源码能在本机编译；Swift 自检通过 9 项动作解码、6 项草稿能力、7 项聊天局部区域选择检查，均无真实 UI 写入或发送。
- 隔离 Git worktree 的 Python 回归 176 项通过；JavaScript 控制器及导航测试 22 项通过。安装目录的 36 项原生后端测试也已复验通过。
- 本机官方微信由 4.1.15 更新为 4.2.0（270353）；安装包通过官方标识、Tencent Team、完整签名及系统公证评估。更新前已备份原客户端和加密数据库。
- 新版登录恢复后，独立联系人副本能够解析唯一目标；显式本机称呼映射也已验证，配置和实际账号不写入仓库。启动同步期间发生过源变化，未把旧副本冒充新证据。
- 当前运行进程的 Security 动态签名检查约 64 ms；不再在每次控件读取时深度扫描整个应用目录。
- 已测试的一次前台只读激活中，官方进程确实成为前台、主窗口 Raise 成功，但主窗节点数仍为 6；focused getter 返回 noValue，客户区只读 hit-test 返回 notImplemented。没有输入、发送或修改系统设置。

## 当前实机阻塞

4.2.0 在本机仍未向普通 AX 客户端暴露搜索框、聊天输入框和发送控件。主窗口同时报告 WindowServer sharing_state=0，普通窗口截图为白屏；这不证明某个具体用户设置已开启，不能擅自绕过捕获排除。

本轮尚未通过自动打开目标聊天、真实草稿准备与清理、一次发送和目标新记录核验的完整实机链路。新的原生控制器会在无法取得当前 UI 身份或控件时返回实际阶段错误，而非无条件假报成功或盲发。

早先一次“用户协助定位后的界面发送 + 目标会话新增记录核验”成功，只证明那条辅助路径；不是新控制器免人工定位的验收。

## 不足以替代当前 UI 证明的线索

会话数据库包含按 username 索引的草稿字段，但尚未验证其编码、落盘时延和 window_id 语义。草稿变化最多能作为曾写入指定目标的额外证据，不能单独证明提交瞬间仍处于同一聊天。HID 聚合事件计数也不能证明没有其他程序或应用内部切换。因此目前没有用这些线索放开盲目键盘发送。

继续实机验收需要可观察的当前聊天/输入框，或另行验证的等价目标证明。保留同一操作编号和一次提交限制；核验失败只重试读取，不重放消息。
