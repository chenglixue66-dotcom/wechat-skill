# 微信发送流程

适用于当前用户明确请求的普通 person 文字单聊；已指定收件人及原文或清楚目的时直接执行，不重复询问同一条消息的发送许可。此流程是当前用户触发的前台操作，不用于后台定时或无人值守发送。群聊、图片、公众号及系统联系人尚未纳入原生实际发送范围。

## 当前状态

截至 2026-11-07：实现与离线测试通过；微信 4.2.0 在本机的界面读取验证受阻，完整免人工定位链路尚未通过。

当前已安装微信 4.2.0（270353）且登录已恢复；前台 AX 仍只返回窗口外壳，搜索框、输入框和发送控件不可读。

历史上曾完成一次用户协助打开目标聊天后的 CUA 文字发送，并核验到唯一新增记录；这不证明新版自动导航验收通过。4.1.15 的空 AX/窗口外壳和自动化白屏样本也不能推广为当前所有版本不可用，或推断用户没有登录。

## 1. 选择有正确效果的命令

```bash
# 只读计划：联系人解析和正文hash，不导航、不写输入框
~/.agents/skills/wechat/scripts/wxsend --dry "小明" --text "测试文字"

# 当前任务授权的无发送实机验证：打开聊天、空框写入、精确清理
~/.agents/skills/wechat/scripts/wxsend --draft-check "小明" --text "测试文字" --operation-id draft_check_001

# 普通实际消息：完整链路，只提交一次并核验
~/.agents/skills/wechat/scripts/wxsend "小明" --text "我下午三点到" --operation-id request_001
```

`--draft-check` 与 `--dry` 的效果不同，不得混用名称或把草稿检查当成只读。`--text-file <路径>` 可替代 `--text`，路径 `-` 表示标准输入。真实发送的操作编号为 `[A-Za-z0-9_-]{1,128}`，同一请求固定不变。

入口优先重新执行到 `~/WeChatDataAnalysis/.venv/bin/python`，这些模块要求 Python 3.10+。只有环境真正缺少依赖或原生桥时才修复安装；不把一次诊断失败扩大成全部发送能力不存在。

## 2. 原生自动控制器

`wxsend` → `wechat_automation.execute()` → 新鲜联系人目录、原生后端、SendGuard 和 ReceiptSession。

1. **解析目标。** `contact_resolver.py` 从配置账号的新鲜 contact-only 副本精确匹配 username、alias、备注、昵称。多个跨字段候选保持歧义；不读大段历史找人。实际控制器只接受 person。
2. **建立基线。** 真实消息先由 `ReceiptSession.prepare()` 对普通消息分片取独立快照，严格建立目标会话基线；失败时不打开聊天。只读计划与无发送草稿检查不需要建立真实提交基线。
3. **打开聊天。** `NativeBackend.open_chat()` 校验官方应用及本次进程，读取账号字段、操作明确搜索控件、选择唯一结果、核对资料卡原始微信 ID，再把实际聊天标题、窗口、输入框和发送对象关联起来。联系人目录不能单独证明当前聊天。
4. **准备输入框。** `SendGuard.prepare()` 重验本次绑定、前台/焦点/在屏/模态、目录新鲜度和空草稿，写入精确正文并回读；已有用户草稿不覆盖。`--draft-check` 到此后精确清理，发送次数必须为 0。
5. **一次提交。** `ReceiptSession.submission()` 先持锁落盘提交意图，Guard 再次检查同一正文及对象，原生后端才对绑定的发送控件调用 AXPress。默认后端及诊断 CLI 没有真实提交权限，实际消息控制器才显式启用。
6. **发后核验。** 再取独立快照，仅检查目标会话的新增本人记录、ID、类型、正文 hash 和时间。提交异常后仍只核验，不授权重发；临时快照读取失败可以只读重试。

状态放在 `~/.config/wechat-skill/` 下私有目录，正文不写入持久日志。新鲜目录具有短 TTL，来源或配置变化时停止，不悄悄替换已经绑定的目录来延长一次操作。

基线已写但协调状态写入失败时，只能在未提交的 PREPARING/BASELINE_FAILED 状态中，经身份、正文 hash、源连续性及锁检查后恢复；提交过的操作不能重置。核验已成功时持久化成功结果，后续 `verify()` 返回 `cached=true`，不会因新的读取故障抹掉过去证据。

## 3. 失败与备用界面路径

- 失败按实际 `stage` 和固定错误码报告；`send_attempts=0` 表示没有进入真正发送动作，不冒称已发。
- 只在实际看到登录页或失效提示时处理登录。不循环 probe、登录或重启；旧 `--probe` 默认 `live_send_permitted=false` 不是所有路径都关闭的证明。
- 若原生布局不支持，CUA 可读取本次 AX 状态，必要时结合新鲜截图进行界面适配。可复用 `cua_chat_controller.cjs`；它不是原生控制器实机验收的替代证据。
- AX 不可读但截图正常时，可以依据新鲜画面核对目标。AX 与截图均不可读时不要猜坐标、覆盖草稿或盲按 Return；准确报告自动化读取问题。只有必要时才请求一次目标聊天定位协助，不重复要发送许可。
- 收件人/账号不一致、已有草稿、来源或窗口漂移时停止。动作结果不明时先核验，不能换操作编号重放。

## 4. 完成证据

`verified` 只证明目标会话出现唯一匹配的新本人发出记录；不证明对方收到或已读。`cached=true` 表示返回既有核验成功，不是新发送。仅按键成功、输入框清空、目录命中或测试通过都不能独立当作消息已经发出。

需要核验实现细节时读 `receipt_session.py`、`snapshot_recipient.py`、`verify_sent.py`；普通执行由统一入口编排，不现场复制一套松散的提交逻辑。开发状态见[发送修复说明](sending-repair.md)。
